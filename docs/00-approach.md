# 진행 방식 설계와 검증

작성일: 2026-08-20

이 문서는 **어떤 방식으로 학습할 것인가**를 정하고, 그 방식이 목표를 실제로 달성하는지 미리 검증한 결과를 담는다.

---

## 1. 채택한 방식

아주 단순한 가정에서 출발해 점진적으로 전체를 구체화하는 **점진적 하향식 설계(gradual top-down design)** 를 뼈대로 한다.

각 층에서 반복하는 절차는 다음과 같다.

1. 현재 층의 그림을 그린다. 구성 요소는 상자로만 표시하고 내부는 비워 둔다.
2. 그 그림을 보면서 "지금 이 상태에서 무엇이 성립하지 않는가"를 찾는다.
3. **최소 구현으로 실제로 한 번 돌려 본다.**
4. 설계상의 모순과 구현에서 드러난 문제, 두 가지 모두에서 다음 층을 도출한다.

3번이 핵심이다. 설계만 계속 정교화하면 목표 3(어떤 문제에 부딪히는가)에 도달하지 못한다. 실제로 부딪히는 문제의 대부분은 도면에 보이지 않고 실행할 때만 드러난다.

---

## 2. 층별 시뮬레이션

### 층 0 — 상자 두 개

```
[코어 AI 엔진]              [고객사 시스템]
```

질문: **고객사의 CS 대응을 이 엔진으로 자동화하려면 무엇이 필요한가.**

성립하지 않는 것: 엔진이 고객사 데이터를 읽을 경로가 없다. 그리고 애초에 처리할 문의가 엔진에 도달할 경로가 없다.

- 도출: 채널(문의 유입), 연동부(엔진과 고객사 시스템 사이)
- 소요: 20분

의도적으로 소비자를 상자로 그리지 않는다. 처음부터 그려 두면 존재가 전제되어 버린다. 두 개에서 출발해야 **소비자와 채널이 도출의 결과로 나온다.**

### 층 1 — 연동 설계 및 구현

```
[고객] → [채널] → [코어 엔진] → [연동부] → [고객사 시스템]
```

새로 드러나는 문제: 엔진이 문의 텍스트를 받았지만 그것만으로는 무엇을 해야 할지 결정할 수 없다. "제 주문 어디쯤 왔나요"라는 문장에서 엔진이 알아내야 하는 것은 세 가지다. **이 고객이 누구인가, 어느 주문에 관한 이야기인가, 무엇을 원하는가.**

또한 조회에 성공해서 "8월 18일 출고, 운송장 12345"라는 데이터를 얻더라도, **이 데이터를 어떤 문장으로 바꿔 답해야 하는지 모른다.** 답변 규정이 고객사마다 다르기 때문이다.

- 도출: 고객·주문 식별, 의도 판단, 규정 저장소, 답변 생성
- 소요: 설계 40분

**구현 순서에 대한 결정**: 연동부를 만들려면 고객사 시스템이 어떻게 생겼는지 알아야 하는데, 고객사 시스템 파악(전환 1)은 뒤에 있다. 두 가지 선택지가 있었다.

| 방법 | 내용 |
|---|---|
| A | 전환 1을 앞으로 당겨 고객사 시스템을 먼저 파악한다 |
| B | **가짜 인터페이스로 먼저 만들고, 나중에 실제에 맞춰 고친다** |

**B를 채택한다.** 실무에서 벌어지는 일이 정확히 B이기 때문이다. FDE는 고객사 API 문서를 받기 전에 설계를 시작하고, 문서를 받고 나서 고친다. 그리고 문서와 실제 동작이 또 다르다. 이 어긋남을 겪는 것이 목표 3에 직결된다.

### 층 2 — 엔진 내부 분해

```
수신 → 식별 → 의도판단 → 규정조회 → 도구호출 → 답변생성 → 발송
```

이 층에서 드러나는 문제는 이전보다 무겁다.

- **도구 호출이 실패하면 엔진은 무엇을 해야 하는가.** "잠시 후 다시 문의해 주세요"라고 답하면 고객은 화가 난다.
- **규정을 조회했는데 그 규정이 이 상황을 다루지 않으면 어떻게 하는가.** 화장품 부작용 문의는 규정 문서에 없을 가능성이 높다.
- **답변이 틀렸는지를 누가 판단하는가.** 엔진 스스로는 판단할 수 없다.

- 도출: 에스컬레이션 경로, 승인 게이트, 실행 로그
- 소요: 설계 1시간 30분 / 구현 3시간

**첫 번째 구현 지점.** 작업자가 코어 루프를 직접 작성한다. 100~150줄 규모이며, LLM에 도구 목록을 넘기고 → 모델이 도구 호출을 요청하면 실행하고 → 결과를 다시 넘기고 → 최종 답변이 나올 때까지 반복하는 구조다.

돌려 보면 설계도에 없던 것이 드러난다. **모델이 도구를 호출하지 않고 답을 지어낸다.** 도구 설명을 어떻게 쓰느냐에 따라 호출률이 달라진다. 이것이 목표 3의 첫 항목이다.

### 층 3 — 연동부 분해

```
주문 어댑터 │ WMS 어댑터 │ ERP 어댑터 │ 택배사 어댑터
```

**FDE 업무의 심장부이자, 하향식 설계의 한계가 분명해지는 지점.** 도면에는 상자 네 개지만 실제로 구현하면 다음이 나온다.

| 설계도에 없던 문제 | 구체적인 내용 |
|---|---|
| 식별자 불일치 | 자사몰 주문은 `ORD-20260815-00123`, 외부 채널 유입 주문은 `31234567890`. 한 어댑터가 두 체계를 다뤄야 한다 |
| 자연어에서 식별자 도출 | 고객이 "지난주에 산 세럼"이라고 쓴다. 이것을 주문번호로 바꿔야 한다 |
| 시스템 간 상품명 불일치 | 어드민에는 "글로우 세럼 30ml", WMS에는 "GLW-SRM-30" |
| 응답 지연 | ERP가 5초 넘게 응답하지 않는다. 계속 기다릴지 포기할지 결정해야 한다 |
| 부분 실패 | 환불 중 ERP는 성공, WMS 반품 등록은 실패 |

- 도출: 타임아웃, 재시도, 멱등키, 보상 처리, 식별자 정규화 계층
- 소요: 설계 1시간 / 구현 5~6시간

### 층 4 — 운영 층

지금까지가 "어떻게 동작하게 만들 것인가"였다면, 여기서는 **"틀렸을 때 어떻게 고칠 것인가"** 를 다룬다.

- 오답을 발견해 프롬프트를 고쳤다. **그 수정이 다른 200개 문의 유형을 망가뜨리지 않았는지 어떻게 확인하는가.**
- 고객사가 환불 규정을 바꿨다. **규정 문서만 고치면 되는가, 프롬프트도 고쳐야 하는가.**

- 도출: 평가 데이터셋, 회귀 검증, 규정과 프롬프트의 분리
- 소요: 설계 1시간 / 구현 3시간

### 층 5 — 온보딩 5단계 밟기

| 단계 | 실제로 하는 일 |
|---|---|
| 1. 자동화 비율 검토 | 가상 문의 로그 300건을 유형별로 분류하고 자동화 가능 비율을 산출한다 |
| 2. 매뉴얼 정리 | 흩어진 규정을 엔진이 읽을 수 있는 형태로 구조화한다 |
| 3~4. 학습 및 배포 | 프롬프트와 도구를 이 고객사에 맞게 조정하고 평가셋을 돌린다 |
| 5. 유지보수 | 새로운 문의 유형이 주입되고, 그에 대응한다 |

- 소요: 4시간

## 3. 목표 달성 여부 검증

| 목표 | 하향식만으로 | 근거 |
|---|---|---|
| 1. 무슨 일을 하는가 | **달성** | 층 5에서 다섯 단계를 직접 밟는다 |
| 2. 구체적 업무 | **달성** | 층 3의 어댑터 작성, 층 5의 매뉴얼 정리가 실제 업무다 |
| 3. 마주하는 문제 | **부분 달성** | 설계도에서 도출되지 않는다. 별도 조치 필요 |
| 4. 시스템 내부 동작 | **완전 달성** | 층 0~2가 정확히 이것을 겨냥한다. 하향식이 가장 잘 맞는 구간 |
| 5. 고객사 시스템 | **미달성** | 작업자가 도출할 수 없다. 주어져야 한다 |

목표 3과 5가 미달이다. 이를 메우기 위해 세 번의 방식 전환을 넣는다.

---

## 4. 하향식이 통하지 않는 네 구간과 전환

### 전환 1 — 고객사 시스템의 실제 모습 (목표 5)

**왜 통하지 않는가**: 하향식은 "무엇이 필요한가"에서 출발한다. 그래서 고객사 시스템을 설계하면 필연적으로 **깔끔한 시스템**이 나온다. 필요한 것만 넣었기 때문이다. 실제 고객사 시스템은 수년에 걸쳐 쌓인 결과물이고 필요 없는 것과 잘못된 것이 섞여 있다.

**핵심**: FDE는 고객사 시스템을 설계하지 않는다. **이미 존재하는 것을 그대로 받아들여야 한다.** 이 사실 자체가 학습 대상이다.

**전환 방식**: 이 구간에서는 하향식을 쓰지 않는다. 고객사 시스템이 완성된 형태로 주어지고, 작업자는 그것을 **읽고 파악하는 작업**을 한다. 출근 첫 주에 하게 될 일이 정확히 이것이다. 의도적으로 결함을 심는다. 문서화되지 않은 필드, 실제와 다른 문서, 반환값이 일관되지 않은 엔드포인트.

### 전환 2 — 의도 체계와 암묵지 (목표 3의 앞부분)

**왜 통하지 않는가**: 하향식으로 접근하면 의도 분류 체계를 머리로 설계하게 된다. 배송·환불·교환 같은 식이다. 그런데 **실제 문의는 그 분류에 깔끔하게 들어가지 않는다.** "어제 주문했는데 색상 잘못 골랐어요 취소하고 다시 주문할까요 아니면 바꿀 수 있나요"는 취소이면서 교환이면서 상담이다.

**전환 방식**: 이 구간만 **상향식으로 뒤집는다.** 실제 형태의 문의 300건이 먼저 주어지고, 작업자가 그것을 읽으면서 분류 체계를 **귀납적으로 도출**한다. 데이터가 먼저이고 설계가 나중이다.

더 중요한 목표가 있다. 고객사의 정책 중 상당 부분은 문서에 없고 **담당자의 암묵지로만 존재한다.** 그것을 문의 데이터에서 역으로 끄집어내어 **결정 가능한 체계**로 만드는 것이 이 구간의 본질이다. 이 순서 자체가 온보딩 1단계와 동일하므로 두 가지를 한 번에 수행한다.

### 전환 3 — 장애 주입 (목표 3의 핵심)

**왜 통하지 않는가**: 정상 경로를 설계할 때 실패 경로는 상상으로만 다루게 된다. "ERP가 실패하면 재시도한다"는 문장은 쉽게 쓴다. 그런데 재시도했더니 환불이 두 번 나가는 상황은 **실제로 겪어야 이해된다.**

**전환 방식**: 별도 트랙으로 장애를 주입한다. **예고하지 않는다.**

| 주입할 장애 | 발견하게 될 것 |
|---|---|
| ERP 응답 지연 5~15초 | 전체 응답 시간 예산을 어떻게 배분할 것인가 |
| 환불 API가 성공 후 타임아웃 | 멱등성이 없으면 이중 환불이 발생한다 |
| WMS 재고가 어드민과 불일치 | 어느 시스템을 진실의 원천으로 삼을 것인가 |
| 부작용 문의 유입 | 법적 의무가 있는 문의는 자동 응답하면 안 된다 |
| 효능 문의 유입 | 표시광고 규제를 위반하는 답변이 생성될 수 있다 |

### 전환 4 — 오퍼레이션 콘솔 (JavaScript 구간)

**왜 통하지 않는가**: JavaScript 경험이 없으므로 **설계와 구현 사이를 왕복할 수 없다.** 설계에서 문제를 도출해도 구현으로 확인할 수 없으면 층이 진행되지 않는다.

**전환 방식**: 이 구간에서는 역할을 **설계자에서 사용자로 바꾼다.** 콘솔은 주어지고, 작업자는 고객사 CS 담당자의 입장에서 그것을 써 본다. 그리고 "이 화면으로는 무엇을 할 수 없는가"를 발견한다.

목적이 달라 보이지만 더 정확하다. FDE가 만드는 도구의 사용자는 FDE 본인이 아니라 **고객사 담당자**이기 때문이다.

## 5. 전환을 넣은 뒤의 목표 달성 여부

| 목표 | 하향식만 | 전환 포함 |
|---|---|---|
| 1. 무슨 일을 하는가 | 달성 | 달성 |
| 2. 구체적 업무 | 달성 | 달성 |
| 3. 마주하는 문제 | 부분 달성 | **달성** (전환 2, 3) |
| 4. 시스템 내부 동작 | 완전 달성 | 완전 달성 |
| 5. 고객사 시스템 | 미달성 | **달성** (전환 1) |

## 6. 시간 예산과 위험

| 구간 | 작업자 시간 |
|---|---|
| 층 0~2 설계 | 2시간 30분 |
| 코어 루프 구현 | 3시간 |
| 전환 1 — 고객사 시스템 파악 | 1시간 30분 |
| 전환 2 — 문의 분류 및 암묵지 도출 | 2시간 |
| 층 3 설계 + 어댑터 구현 | 6시간 |
| 전환 3 — 장애 대응 | 3시간 |
| 층 4 + 콘솔 사용 | 2시간 |
| 층 5 — 온보딩 5단계 | 4시간 |
| 정리 문서 작성 | 2시간 |
| **합계** | **약 26시간** |

2~3일 기준으로 빠듯하다. 위험과 완화책은 다음과 같다.

| 위험 | 완화 |
|---|---|
| 층 3에서 시간이 초과된다 | 어댑터 하나(ERP)만 깊게 만들고 나머지 셋은 인터페이스만 맞춘 얕은 구현으로 둔다. 깊이는 하나에서만 경험해도 충분하다 |
| 설계 단계가 길어진다 | 각 층에 시간 상한을 두고, 상한에 닿으면 미완성이어도 구현으로 넘어간다 |
| Python 문법에서 막힌다 | 즉시 묻고 넘어간다. 문법 학습은 이 프로젝트의 목적이 아니다 |
